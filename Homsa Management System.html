Homsa Travel Management System

A single web platform that brought public relations, leads, subscriptions, accommodation and customer follow-up into one place, and connected them from the first lead to the customer's return from the trip.

Overview

One system instead of scattered data

I designed and built a complete web system for Homsa Travel that lets every department work on the same data. A public relations employee registers a lead. When the lead subscribes, a subscription is created automatically. The accommodation team assigns the trip, hotel and room in Makkah and Madinah. The call center records the customer's feedback after the trip, and management follows performance and targets from the same screen.

The system runs on Google Sheets as the database and Google Apps Script as the backend, so the company uses it without servers or hosting fees, and can open the sheet and review the data at any time.

Problem

Each department kept its data somewhere else

The company's work passes through several departments: in-office and field public relations, subscriptions, accommodation, call center and accounting. When customer data lives in more than one file, familiar problems appear:

  • The same customer is entered more than once, and the copies drift apart.
  • There is no quick way to see who is responsible for a customer or how they reached the company.
  • Moving a lead to a subscriber, and then to accommodation, meant copying data by hand between files.
  • Tracking each employee's and team's performance against their goals was calculated manually.
  • Each employee should see only their own data, which is hard to guarantee when a file is open to everyone.
Goal

Enter data once, and show each role only what it needs

I set three goals: data is recorded once and flows between departments without retyping, every employee sees and edits only what concerns them, and management can measure performance and reward results using real numbers from the same data.

Solution

The customer journey inside the system

I built the system around the real customer journey, so each stage hands off to the next without duplicate entry.

  1. Lead or agent registeredAutomatic customer code, source, and responsible employee.
  2. Converted to subscriberChanging the status to "subscribed" opens a required receipt form and creates the subscription automatically.
  3. Lottery and tripLottery status, and linking the subscriber or winner to a trip.
  4. AccommodationA hotel and room in Makkah, and a hotel and room in Madinah, for each person.
  5. Travel and follow-upTravel status, then a feedback call from the call center after the trip.

Architecture

Three simple layers, no server to maintain

Interface

One Arabic, right-to-left page that works on desktop and mobile.

⇄

Backend

Google Apps Script: login, session verification, and permission checks on every request.

⇄

Database

Google Sheets: one sheet per section, which the company can review and export at any time.

The interface never reads the sheet directly. Every read and write goes through the backend, which decides whether the user is allowed and returns only the permitted rows.

Roles

Each role sees its own work

Default permissions come from the role, and the admin can customize them for any employee at the section level. Each section also has a visibility scope: all employees, the employee's team, or only the employee's own records.

Challenges

Problems I hit and how I solved them

Slow Google Apps Script
Browser-side caching, merging simultaneous reads into one request, a server cache versioned per table that refreshes the moment anything is written, and loading the remaining sections in the background after the first screen appears.
Concurrent writes from different users
A server lock that runs writes one after another, so two requests never write to the same empty row.
Edits lost when the connection drops
Each edit shows on screen immediately and goes into a queue that syncs in the background with automatic retries, plus a warning before closing the page if anything is still unconfirmed.
Names typed differently
One name can be written with or without hamza or with extra spaces, which made employees lose sight of their own records. I unified matching by normalizing names with the same rule in the interface and the backend.
Dates shifting by a day
Timezone differences between the browser and the sheet showed a different day than the one picked. I now read date parts straight from the text and store dates in the sheet's own timezone.
Input turning into formulas
Any text that starts with a formula character is sanitized before it is written to the sheet, so entered data can never run as a command.
Security

Permissions are enforced on the server

  • Signed, time-limited login sessions tied to a per-user version, so logging out or changing a password invalidates old sessions.
  • Passwords are stored hashed with a per-user salt and repeated hashing, never shown after saving, and the users table never returns sensitive fields to the browser.
  • Failed login attempts are rate limited with a temporary lockout.
  • The backend checks the role and record ownership on every request, so editing the page in the browser never unlocks extra access.
  • The edit log stamps the user on the server, so nobody can write under someone else's name, and old entries are archived automatically.
  • Salary, national ID and address fields are removed from responses for any role other than management and HR.
Impact

What changed after the system

  • Customer data is recorded once and moves from lead to subscription to accommodation, instead of being retyped in each department.
  • Every employee sees their own numbers, targets and incentive without asking anyone.
  • Management compares teams and employees using real numbers from the same data.
  • Every change can be traced: who edited what, when, and with which value.
